## 1. Summary

- **No Critical or High defect was found in Krova's own code.** There is no networking code, no window-title access, and no logging of anything sensitive. Those privacy promises hold *at the source level* (section 3).
- **Three Medium items**, all about shipping rather than about a demonstrated exploit: unsigned installers (F-01), a release pipeline that floats its tool versions and auto-publishes on a tag (F-02), and a macOS layer of hand-declared FFI that has never been compiled or run (F-03).
- **The privacy page is wrong or incomplete in five places** (section 3.2). The biggest: "Krova keeps one file" is overstated (a WebView2 profile folder, the autostart entry and a few transient files also exist), and the macOS Input Monitoring prompt is not mentioned.
- Eleven Low and five Info findings are hardening and robustness items (section 4).
- Counts: Critical 0, High 0, Medium 3, Low 11, Info 5.

Before a first public release, in order: fix the privacy page wording (F-14), sign the artifacts (F-01), pin the release toolchain and gate publishing (F-02), and do not ship the macOS build until it has been compiled and exercised on a Mac (F-03).

## 3. Privacy promises

### 3.1 What `config.json` really contains

Defined in `config.rs:60-144` and written with `serde_json::to_vec_pretty` (`config.rs:202`):

- `schema_version`.
- `settings`: `enabled`, `modifier`, `highlight_color`, `highlight_opacity`, `move_mode`, `edge_snapping`, `edge_size_px`, `launch_at_login`, `theme`.
- `monitors[]`, each: `id` (`monitor-N`), `label` (set equal to the id, `config.rs:104`), `hardware_id`, `device_path`, `last_rect` (x, y, w, h in pixels), `layouts[]` (layout `id`, `name`, zones with numeric `id` and normalised `rect`), `active_layout`.

There is no field for any window, process, application, title, cursor path or timestamp. The engine writes the config only through `refresh_monitors` (monitor geometry and ids) and the layout/settings commands.

What the identifiers are:

| | Windows | macOS (never compiled) |
|---|---|---|
| `hardware_id` | PnP id such as `DELA0B7`, parsed from the display's device-interface name (`win.rs:277-290`, `ids.rs:12-25`). **No EDID serial.** | `VVVV-MMMM-SSSSSSSS` from `CGDisplayVendorNumber/ModelNumber/SerialNumber` (`mac_screens.rs:73-78`, `mac_math.rs:105-111`). **Includes the display serial** when non-zero. |
| `device_path` | The full interface name, e.g. `\\?\DISPLAY#DELA0B7#5&2d2b8a8f&0&UID4353#{guid}` (`win.rs:286-291`); includes a per-adapter/port instance id. | The display UUID string (`mac_screens.rs:172-178`). |
| `last_rect` | Last seen monitor rectangle. Used only for equality in scoring (`monitor.rs:20-43`), never in arithmetic. | same |

All of these also travel to the webview inside `AppState` (`commands.rs:34-38`, `model.rs:55-63`); the UI does not use them beyond display.

Other places where Krova causes data to exist on disk or in the registry (none is mentioned on the privacy page):

- Windows WebView2 profile: Tauri forces the webview data directory to `app_local_data_dir()`, i.e. `%LOCALAPPDATA%\dev.krova.app` (`tauri-2.12.5/src/manager/webview.rs:559-569`); WebView2 keeps its Chromium profile data there (cache, local state and similar). Not observed on disk (app never launched).
- macOS WKWebView storage under `~/Library/WebKit` and `~/Library/Caches` (standard behaviour, not verified).
- Autostart: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Krova` (`win.rs:69-70,701-715`); on macOS a Login Item via `SMAppService` or `~/Library/LaunchAgents/dev.krova.app.plist` (`mac_autostart.rs`).
- Transient: `config.json.tmp` during a save; `config.json.bak` after a recovery.
- macOS only: `/tmp/dev_krova_app_si.sock`, the single-instance socket (plugin, `platform_impl/macos.rs:73`).
- Windows only: a named mutex and hidden window for single-instance (no file).

### 3.3 Suggested corrections (for the owner of `privacy.astro` and SPEC 1.10)

1. Replace "Krova keeps one file" with: settings and layouts live in one file, `config.json`; separately, Windows stores the embedded browser's profile under `%LOCALAPPDATA%\dev.krova.app`, "Launch at login" adds a registry entry (Windows) or a login item/LaunchAgent (macOS), and a `config.json.tmp`/`.bak` may exist. Say how to remove each.
2. Add one sentence to "What Krova does not record": Krova listens to mouse movement and clicks system-wide while it runs (it needs this to notice a window drag), checks the state of the activation key and Escape during a drag, and checks whether the window's program runs as administrator; none of this is stored or sent.
3. Under network: add that the Windows installer downloads Microsoft's WebView2 runtime if it is not already installed, and that the WebView2/WebKit runtimes are separate OS components.
4. Say that the macOS display serial number is stored and that Windows does not store one.
5. Under permissions (macOS): mention Input Monitoring once confirmed on a real Mac.

## 5. Area notes (what was checked, including what was found sound)

### 5.1 Tauri attack surface

- **CSP and capability.** `csp`: `default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost`. There is no `script-src`, so scripts fall back to `'self'` (inline scripts blocked). `withGlobalTauri` is false. The `tauri` crate is built without the `devtools` feature (`src-tauri/Cargo.toml:19`). `capabilities/default.json` grants only `core:event:default` to window `main`; no fs, shell, http, opener, dialog or updater plugin exists in the dependency list. No deep-link or custom URL scheme is registered. No code or config requests elevation (grep for `requestedExecutionLevel` and `requireAdministrator` in `src-tauri`: none; the generated manifest was not inspected).
- **UI.** No `{@html}`, `innerHTML`, `eval`, `new Function`, `fetch`, `XMLHttpRequest`, `WebSocket`, `window.open`, `localStorage` (outside the browser-only mock backend, `mockBackend.ts`) or external URL in `ui/src`. User-supplied strings (layout and monitor names) are rendered through Svelte text interpolation. `highlight_color` is bound with `style:background=` (one CSS property).
- **Commands** (`commands.rs`). `Settings` and `Layout` arrive as serde-typed values, so enum fields cannot hold arbitrary strings.

| Command | Input | Validation before persist/act | Persists? |
|---|---|---|---|
| `get_state` | none | n/a (also refreshes monitors, may start input) | monitor geometry only |
| `save_settings` | `Settings` | `sanitize_settings` clamps opacity, edge size, colour (`model.rs:150-163`) | yes |
| `save_layout` | monitor id, `Layout` | `Layout::validate` (`config.rs:265`) and the monitor must exist; **no size caps** (F-04) | yes |
| `delete_layout` | ids | ids must exist; last layout refused | yes |
| `set_active_layout` | ids | layout must exist | yes |
| `list_templates` | none | n/a | no |
| `edit_split_zone`, `edit_remove_zone`, `edit_move_divider` | `Layout` + numbers | **none** before the edit; results are revalidated only if later saved (F-09) | no |

- **Single instance.** Windows: named mutex plus hidden window; `WM_COPYDATA` from any same-integrity process reaches the callback, which ignores its arguments and only shows the editor (`lib.rs:23-25`). macOS: see F-13.
- **Tray and menu.** Handlers match five static ids (`tray.rs:66-88`); no external input. `Quit` calls `app.exit(0)`. Closing the window hides it (`lib.rs:38-44`).

### 5.2 Unsafe Rust

`krova-core` has `#![forbid(unsafe_code)]` (`crates/krova-core/src/lib.rs:3`). `src-tauri/src` contains no `unsafe`. In `krova-platform`, lines containing `unsafe`: `win.rs` 39, `win_overlay.rs` 14, `mac_ffi.rs` 22, `mac_ax.rs` 12, `mac_input.rs` 8, `mac_overlay.rs` 8, `mac_screens.rs` 8, `mac_autostart.rs` 5, `mac.rs` 4 (counts include comments and `unsafe fn` signatures).

**Windows (`win.rs`, `win_overlay.rs`) looked sound.** Typed `windows` 0.58 bindings, no `static mut`.
- `zeroed()` is used only for plain-data structs (`MONITORINFOEXW`, `DISPLAY_DEVICEW`, `WNDCLASSEXW`, `BITMAPINFO`), where all-zero is valid.
- `collect_monitor` casts `data` back to the `Vec` that outlives `EnumDisplayMonitors` (`win.rs:247-253,586-593`).
- `mouse_proc` dereferences `lparam` as `MSLLHOOKSTRUCT` only when `code >= 0`, as documented (`win.rs:347-351`).
- `win_overlay` registers the class (the name is copied by `RegisterClassExW`) and creates the window while the class-name `Vec` is alive (`:107-134`); all window calls for the overlay happen on its own thread; GDI objects are released on every path in `paint` (`:196-256`). The one gap is F-16 (`paint` trusts the buffer length).
- Handle values cross threads as `u64` (`WindowId`) and are re-checked with `IsWindow` before use; HWND recycling between press and release is theoretically possible and would only move another window of the same user.

**macOS (`mac_*.rs`) cannot be called sound, only plausible** (F-03). What I checked:
1. *ABI shapes.* `msg_rect` uses `objc_msgSend_stret` on x86_64 and a plain `objc_msgSend` returning an HFA on aarch64 (`mac_ffi.rs:335-361`); that is the correct split in principle. `CGRect` is passed by value to `setFrame:`, `setFrame:display:` and `initWithContentRect:...` (`:319-332`), and `BOOL` as `u8`. The constants (event types, tap placement, `kCFNumber*`, AX value types, `CGWindowList` options, bitmap info) match the documented values as far as I know. The `CGEventTapCallBack`, `CGImageCreate` and `CFDictionaryCreate` signatures match the headers as I remember them. None of this was compiled.
2. *Objective-C exceptions.* A wrong selector or a nil argument raises an `NSException` that would unwind through Rust frames (undefined behaviour or abort). `respondsToSelector:` guards exist only for `localizedName` and the `SMAppService` selectors (`mac_screens.rs:126`, `mac_autostart.rs:63,72,79`); every `NSWindow`, `CALayer`, `CATransaction`, `NSScreen`, `NSString` and `NSNumber` call in `mac_overlay.rs:158-251` and `mac_screens.rs:33-155` is unguarded.
3. *Threads.* `NSScreen` and `NSWindow` work is funnelled to the main thread through `run_on_main`/`dispatch_main` (`mac_ffi.rs:529-566`), with a panic guard and an autorelease pool. Risks: `run_on_main` gives up after 3 s but the queued closure still runs later (a window nobody owns); `get_state` runs on the main thread and may call `start_input`, which waits up to 2 s (`mac_input.rs:267`); AX calls run on the engine and worker threads, and I cannot confirm Apple supports that.
4. *Ownership.* Create/Copy results are wrapped in `CfOwned` and released on drop; `CFArrayGetValueAtIndex`/`CFDictionaryGetValue` results are treated as borrowed; the AX window element returned by `find_window` is borrowed from an array that outlives it (`mac_ax.rs:329-357`); the tap's port, source and retained run loop are each released once (`mac_input.rs:144-148,301-309`). Leak on the start-timeout path (`mac_input.rs:273-279`): a retained run loop and an orphan tap thread, and `RUNNING` is reset so a second tap can start. Not unsound.
5. *Event tap.* Created with `kCGEventTapOptionListenOnly` (`mac_ffi.rs:111`, used at `mac_input.rs:110`), so it cannot modify or block events; the callback only forwards left-mouse positions and re-enables the tap if the system disables it (`:59-90`). `info` points into a `Box` that outlives the tap (`:100-105,144-151`).
6. *Private or optional symbols.* `_AXUIElementGetWindow` and `CGDisplayCreateUUIDFromDisplayID` are resolved with `dlsym` and transmuted to assumed signatures, with a fallback when missing (`mac_ax.rs:262-271`, `mac_screens.rs:161-170`).
7. *Strings.* `cf_string_to_rust` uses a fixed 256-byte buffer and returns `None` on overflow (`mac_ffi.rs:460-466`): benign.

### 5.3 Global mouse hook and event tap

Windows (`win.rs:343-449,462-579`):
- **Can it swallow input?** No. `mouse_proc` always ends in `CallNextHookEx` and never returns a non-zero "handled" value (`:372`). It reads only the cursor point, no key data.
- **Can it deadlock or stall input?** The callback does an atomic store, a non-blocking `try_lock` on `HOOK_TX`, and an unbounded `mpsc` send (`:365-367`); `HOOK_TX` is never held across a blocking call, and its only blocking users (`spawn_hook_thread`, `clear_hook_slot`) hold it briefly. Heavy work (`WindowFromPoint`, process queries, a 30 ms sleep on release) is on the separate worker thread. A contended `try_lock` drops that event (a lost button-up is superseded by the next press, `snap.rs:276-285`).
- **Leaks.** `InputHandle`'s drop posts `WM_QUIT`, joins both threads and clears the slot (`:684-689`), but the handle lives in `Shared.input` for the process lifetime, so in practice the OS tears the hook down at exit. Edge cases are in F-10.
- **If the app crashes or is killed while hooked.** The hook belongs to the process; Windows removes it on termination. Nothing persists (no service, no driver, no registry hook entry). If the process *hangs* rather than dies, input waits up to the system's low-level-hook timeout per event, after which Windows may drop the hook (documented; not reproduced). A panic inside `mouse_proc` would abort the process on current Rust (it is `extern "system"`), but I found no panicking path there.
- **Injected events** are treated like physical ones (F-15).
- **Keys.** Only Shift/Ctrl/Alt/Win and Escape state is polled, and only around a drag (`:468,503,568-577`).

macOS: a listen-only tap (it cannot swallow input by construction), left-mouse events only (`mac_input.rs:40-42`), key state polled through `CGEventSourceFlagsState`/`KeyState`. Crash behaviour is the OS default (tap destroyed with the process); not tested.

### 5.4 `config.json` handling

- **Atomic write.** Create the directory, write `config.json.tmp`, `sync_all`, rename over the target (`config.rs:197-210`); concurrent writers are serialised by the model mutex and the single-instance guard. Gaps: F-17.
- **Corrupt file.** Unparseable JSON, or JSON that does not fit the schema, is renamed to `config.json.bak` and defaults are used (`config.rs:165-168,179-182,191-194`); an I/O error other than "not found" (for example permission denied) leaves the file alone and disables saving (`lib.rs:64-69`). Gaps: F-07.
- **TooNew.** A `schema_version` greater than the supported one returns `ConfigError::TooNew` and the file is untouched (`config.rs:173-178`, test at `:462-471`). Gap: silent, and the truncation in F-07.
- **Path handling.** The path comes from Tauri's resolver, not from user or webview input; no command accepts a path. If the app-data directory cannot be resolved, `setup` fails (`lib.rs:56`) and the app does not start.
- **Hostile contents.** Invalid layouts are dropped at load (`config.rs:127-135`); NaN cannot occur in JSON, and non-finite or negative rects fail `Rect::is_valid` (`geometry.rs:27-38`); `last_rect` is only compared (`monitor.rs:20-43`); `edge_snap` returns `None` for a non-positive edge size and does no arithmetic on a large one beyond comparisons (`edge.rs:23-31`). Unbounded counts and sizes: F-04, F-05. Settings not sanitised on load: F-06. Monitor-id and layout-id uniqueness is not enforced on load, so duplicates resolve to the first match (harmless).

### 5.5 Elevated windows (UIPI) and hostile windows

- Elevated targets are skipped at press time (`win.rs:496`, `199-215`); if the owning process or its token cannot be opened the window is treated as protected (fail closed, `:208-212`), and an `ERROR_ACCESS_DENIED` from `SetWindowPos` becomes `Refused` (`:317-318`). If the user runs Krova elevated, `self_elevated()` switches that check off (`:199-202`) and Krova can then move any window; there is no "run as administrator" mode and none is recommended.
- What an attacker-controlled (same-user, non-elevated) window can do: be resized or moved as the user's drag target (its own window only); spoof a shell class name to opt out; sit invisibly under the cursor so Krova acts on it instead of the visible window; report extreme geometry (F-16); stall the engine by not answering `SetWindowPos` (F-11); post `WM_COPYDATA` to the single-instance window to bring up the editor, or `WM_CLOSE` to the `KrovaOverlay` window to kill highlights until restart (`win_overlay.rs:98-105` forwards to `DefWindowProc`). None of these reads or exfiltrates anything and none crosses a privilege boundary. An elevated window cannot be steered through Krova because Krova is not elevated.

### 5.6 Supply chain and CI

- Section 2 and F-02, F-12 cover audit output, lockfile hygiene and the release workflow. `ci.yml` uses `pull_request` (not `pull_request_target`), `permissions: contents: read`, and no secrets; it caches Rust builds with `Swatinem/rust-cache@v2`. There is no dependency-audit job and no Dependabot file.
- `tauri-plugin-single-instance` pulls `tokio` with the `net` feature on every platform, so tokio's socket types are compiled into the app even though Krova never calls them. If "no network code" is read as "no socket code in the binary", that is the one exception; it is third-party and idle on Windows.
- Windows build: unsigned (F-01). `tauri.conf.json` has no `webviewInstallMode`, so the default bootstrapper download applies (C1).

## 6. Residual risks (after the fixes above)

1. **No runtime evidence.** The app has never been launched. Network silence, files created, hook behaviour and tray behaviour are inferences from source. A first run under a network monitor and a file/registry tracer should close this.
2. **macOS layer.** Uncompiled FFI in a privileged process; treat as unverified until a Mac test pass.
3. **Components Krova does not control.** The WebView2 (Windows) and WKWebView (macOS) runtimes, OS crash reporters, GitHub's download logging. Their behaviour is outside what the privacy page can promise for Krova itself.
4. **Large dependency tree.** 472 crates in the app lockfile (Tauri, wry, `windows`); `cargo audit` covers only known advisories.
5. **Trust optics of a global input hook.** Even with signing, a tool that watches all mouse input will attract suspicion and heuristic detections; open source and the verification steps in `SECURITY.md` are the mitigation.
6. **Same-user attackers.** `config.json`, the HKCU Run entry and the app-data directory are writable by any process in the user's session. Krova does not (and cannot usefully) defend against that.
7. **Single AI-assisted reviewer.** No fuzzing, no dynamic analysis, no second pair of eyes. PROGRESS.md and README list an independent review as outstanding; this document does not replace it.
